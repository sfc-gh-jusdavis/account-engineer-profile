# Overlay: PDF

PDF-specific application of the four creation principles, plus three skeletons for the most common ACE PDF types.

For the underlying principles see [../creation-principles.md](../creation-principles.md). For workflow patterns see [../creation-patterns.md](../creation-patterns.md). For the actual rendering pipeline (audience workflow, references validation), use the `snowflake-pdf` skill.

---

## The Four Principles for PDFs

### 1. Think Before Creating

Before any drafting, surface and confirm:

| Question | Why it matters |
|---|---|
| **Audience?** customer-facing / internal / partner / field-only | Drives voice, terminology, link policy, classification (the snowflake-pdf skill enforces this via front-matter) |
| **Scope: what's IN?** | The reader needs to know what they will accomplish |
| **Scope: what's OUT?** | An explicit non-goals list prevents reader frustration |
| **Prerequisite knowledge level?** | Determines how much foundational explanation belongs in the doc |
| **Approximate length target?** | A 3-page quickref needs a different structure than a 20-page runbook |
| **What does success look like for the reader?** | This becomes the verification at the end of the doc |

If you can't answer these, **stop and ask the user** before drafting.

### 2. Minimum Viable Asset

PDF anti-patterns to avoid:

- "Background" sections longer than the procedural sections
- Speculative troubleshooting (only document failure modes you've actually observed in the field or seen documented)
- "Advanced" / "Optional" / "Future considerations" sections nobody asked for
- Repeating context that the audience already has (an internal-audience doc explaining what Snowflake is)
- Per-step screenshots of every UI when one screenshot per logical group would serve

The test: would a reader rather have this 12-page guide or the 4-page version of the same content?

### 3. Surgical Edits

When updating an existing PDF:

- Touch only the changed procedure / section
- Don't re-flow the whole doc to fix one paragraph
- Don't reorder sections without explicit ask
- Don't "improve" prose adjacent to a procedure update
- Don't update the references list unless your change adds or removes references

If you notice unrelated issues (typos, outdated links, dead steps), surface them as a list to the user — don't drive-by-fix.

### 4. Verification-Driven Output

Every procedural step ends with a verifiable check:

```
Bad:  "3. Configure SCIM in Entra."
Good: "3. Configure SCIM in Entra: navigate to ... and set ...
       Verify: in Entra's Provisioning logs, the most recent entry shows 'Sync started' within 60 seconds."
```

The whole guide ends with a single end-to-end verification: the canonical "is it working" check the reader runs to confirm everything succeeded.

## Skeleton 1: Setup Guide (SSO / SCIM / Private Link / IdP integration)

```markdown
---
title: <Setup Goal>
audience: customer-facing | internal | partner | field-only
classification: <derived from audience>
date: <date>
---

# Overview

One paragraph: what the reader accomplishes by following this guide.

## What This Guide Covers
- Bullet 1
- Bullet 2

## What This Guide Does NOT Cover
- Bullet 1 (with pointer to where to find it)
- Bullet 2

# Prerequisites

A checklist the reader confirms BEFORE step 1. Each item is verifiable:

- [ ] Snowflake edition: Enterprise or higher. Verify: `SELECT CURRENT_ACCOUNT_NAME(), CURRENT_REGION();`
- [ ] IdP admin access (specific permission)
- [ ] Network reachability between IdP and Snowflake account

# IdP / Cloud-Side Configuration

## Step 1: <action>
Procedure (numbered).
**Verify:** <observable outcome>

## Step 2: <action>
...

# Snowflake-Side Configuration

## Step 1: <action>
**Verify:** <SQL query or UI check>

## Step 2: <action>
...

# End-to-End Test

The canonical check that everything works together.

# Troubleshooting

Only failure modes you've actually observed.

| Symptom | Cause | Fix |
|---|---|---|
| ... | ... | ... |

# References

(Generated by snowflake-pdf skill from validated candidates.)
```

## Skeleton 2: Troubleshooting Guide (existing-issue diagnostics)

```markdown
---
title: <Symptom> Troubleshooting
audience: ...
classification: ...
date: ...
---

# Symptom

What the reader is seeing. Specific, with actual error text or screenshot.

# Quick Diagnostic Checklist

Five-minute triage:

- [ ] Check 1 -> if YES, see Cause A
- [ ] Check 2 -> if YES, see Cause B
- [ ] Check 3 -> if YES, see Cause C

# Cause A: <name>

## How to confirm this is the cause
A specific test that produces an unambiguous YES/NO.

## Resolution
Step-by-step.
**Verify resolution:** <observable outcome>

# Cause B: <name>
...

# When None of These Match

What to capture before opening Snowflake Support / escalating: logs, queries, version info, exact error text.

# References
```

## Skeleton 3: Architecture / Reference Doc

```markdown
---
title: <Topic> Architecture
audience: ...
classification: ...
date: ...
---

# Purpose

The decision or question this document supports. One paragraph.

# Audience Context

What the reader knows and doesn't know going in. One short paragraph — no condescension.

# The Architecture

A diagram (mermaid or image) and a description of the components and their relationships.

# Component Details

Per component:
- What it does
- Inputs / outputs
- Failure modes
- Capacity / limits relevant to this audience

# Tradeoffs and Alternatives

If applicable: what other shapes were considered, why this one was chosen.

# Open Questions / Risks

Honest list. Not "no known risks" unless that's true.

# References
```

## Quality Checks (Before Render)

After drafting and before rendering via the snowflake-pdf skill:

- [ ] YAML front-matter has `audience` set
- [ ] Every procedural step has a verification line
- [ ] No "TODO" / "TBD" / "[fill in later]" markers
- [ ] All commands work as written (you ran them)
- [ ] All UI paths match current product (you walked them)
- [ ] No customer-confidential content unless audience explicitly allows
- [ ] References section will resolve via snowflake-pdf's validation workflow
- [ ] Specialized reviewer subagents were spawned for non-trivial guides (see [reviewer-prompts.md](reviewer-prompts.md))
